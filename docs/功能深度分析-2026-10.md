# 兰台（Lantai）功能深度分析报告

> 分析日期：2026-10-16
> 分析视角：**功能设计本身**，而非"实现是否彻底"。核心问题是——这个功能值得存在吗？它解决了真实痛点吗？它形成闭环了吗？
> 上一份报告（`docs/工具实现审计-2026-10.md`）看的是"写得对不对"，本报告看的是"做得值不值、用起来顺不顺"。

---

## 零、一句话结论

兰台的**工程健壮性扎实**（StepCard 分步引导、批量逐文件容错、Zip Slip 防护、GBK 兜底、身份证校验位、撤销日志、非破坏式去重），但**功能设计层面存在三类系统性缺陷**：

1. **能力取子集**——大量功能只做了"最常见的那一种情况"，一旦数据稍有变化就失效，且**不告诉你为什么失效**。
2. **参数大面积写死**——用户看到的是控件，实际能调的却很少，剩下的是硬编码常量。
3. **缺反馈闭环**——没有预览、没有确认、失败静默、错误信息指向用户做不到的操作。

下面按"严重程度 × 修复价值"排序展开。

---

## 一、最高优先级：功能设计缺陷（影响正确性/可信度）

### 1.1 表格匹配/比对：整个功能的可靠性基础是错的

这是全项目**风险最高**的功能，因为它输出的是"看起来权威的结论"，但结论可能失真。

**问题 A：关联键归一化几乎为零 → 该匹配的匹配不上**

- `normalizeKey` 只做 `trim()` + 去 `.0` 后缀（`excelMatchService.ts:8-12`）。
- **不做大小写归一、不做全半角归一、不做内部空格处理**。
- 主表键 `ABC-001`、副表键 `abc-001` → 全部判为"未匹配"。
- 讽刺的是：**同一个项目的 Excel 合并功能是有全半角归一化的**（`excelToolsService.ts:103`），两个功能策略不一致，用户无法理解为什么 A 能对上、B 对不上。
- 台账场景最常见的就是"全角括号/半角括号""中文逗号/英文逗号""前导空格"差异，这里全部失守。

**问题 B：一对多关联静默丢数据（比对模式尤其危险）**

- `buildLookup` 遇重复 key **只保留首行**（`excelMatchService.ts:52-62`）。
- 匹配填充模式尚可：会通过 `dupKeys` 回传并在 UI 弹黄条警告（`MatchView.vue:271-277`）——这是设计较完善的一处。
- **但比对模式（`compareTables`）复用同一个 `buildLookup`（`excelMatchService.ts:138-139`），重复键丢行时没有任何提示**。
- 后果：一份"一个单位多条记录"的台账，比对报告的"新增/删除/变更"计数**全面失真，且用户毫不知情**。这类报告往往要送审、要签字，错误代价高。

**问题 C：只读第一个工作表 + 硬编码第 1 行为表头**

- `readTable` 用 `worksheets[0]`（`excelMatchService.ts:23`）、硬编码第 1 行为表头（`:26`）。
- 而 Excel 合并功能支持 `headerRow` 参数（`excelToolsService.ts:101`）——**同一项目里，台账表头在第 2/3 行的情况，合并能处理、匹配却不行**。
- 数据在 Sheet2 则完全无法使用，UI 也没有工作表选择器（`MatchView.vue:156,175,208,227` 均写"取第一个工作表"）。

**问题 D：比对是"值精确相等"，无任何容差**

- 逐列用 `cellText(...).trim() !== cellText(...).trim()`（`excelMatchService.ts:154-156`）。
- `1` vs `1.0`、日期格式差异、内部空格差异 → 全部误报"变更"。
- **无"忽略大小写 / 忽略空白 / 数值容差"选项**。

> **修复建议（按价值排序）**：
> 1. 把 `excelToolsService.ts` 里的 `norm`（去空白 + 全半角括号归一）**提升为共享工具**，匹配/比对/合并统一调用，并扩展为"去全部空白 + 大小写归一 + 全半角归一"。
> 2. `compareTables` 必须**显式报告重复键丢行**（复用 `dupKeys` 机制），或改为"行级比对"。
> 3. 给匹配/比对补 `headerRow` 参数与工作表选择器，与合并功能对齐。
> 4. 增加"忽略大小写/空白"开关。

---

### 1.2 环境探测与功能页脱节 → "能点但注定失败"

- 设置页有完整的环境探测（`envProbe.ts:86-113`，UI 在 `SettingsView.vue:268-288`），文案甚至明确写"显示未检测到则该功能会报错"。
- **但转换页 `ConvertView.vue` 全文没有任何 `probe` 引用**——用户必须自己先去设置页看探测结果，再回到转换页操作。
- 后果：没装 Office/WPS 的机器上，用户能选文件、能点"开始转换"，**直到转换中途才失败**，且错误信息笼统（`officeToPdfService.ts:169-171`：`没有产生任何转换结果，请确认本机已安装 Office 或 WPS`），**无法区分"没装"和"文件被占用"和"被杀软拦截"**。

> **修复建议**：转换页进入或选文件时调用一次探测，未检测到直接**在页面顶部给出醒目提示并禁用"开始转换"按钮**，附一键"去设置页查看详情"。

### 1.3 文档模板填充：三端行为不一致，且预览与执行会"打架"

**问题 A：预览说"识别到了"，执行却报错**

- Word 模板的字段扫描直接对整个 XML 做正则 `matchAll(/\{([^{}]+)\}/g)`（`excelService.ts:60`），**能扫到被 Word 拆成多个 run 的占位符**。
- 但实际渲染交给 docxtemplater（`wordService.ts:20-31`），**跨 run 拆分的占位符会失败**。
- 于是出现最伤用户信任的场景：**预览显示"检测到 5 个字段"，一点生成 → 报错说字段识别不了**。

**问题 B：同一套占位符语法，三种格式对"缺字段"处理完全不同**

| 格式 | 缺字段的行为 | 证据 |
|---|---|---|
| Word | 抛错 | `wordService.ts:22-31` |
| PPT | 抛错（`undefined` 时；空串则替换为空） | `pptxTemplate.ts:103` |
| Excel | **静默保留原样 `{字段}`** | `fileUtils.ts:45` 返回 `whole` |

用户用同一份数据、同一套模板，换一种格式就得到完全不同的结果，且没有任何说明。

**问题 C：PPT 填充的硬边界从不提示**

- 只改写 `ppt/slides/slideN.xml`（`pptxService.ts:11`），**备注页（notesSlides）里的占位符永远不生效**——用户若在演讲者备注写 `{字段}`，石沉大海，无任何提示。
- **跨段落占位符不支持**（`{` 在段尾、`}` 在下一段），`PARAGRAPH_RE` 按段切分（`pptxTemplate.ts:82`），同样无提示。

**问题 D：Excel 填充能力最弱，却最容易被误用**

- `fillWorkbook` 只处理 `typeof cell.value === 'string'` 且含 `{` 的单元格（`excelService.ts:14`）。
- **数字型、公式型、富文本型单元格中的占位符静默不替换**——用户看到格子里的 `{姓名}` 没变，不知道为什么。

> **修复建议**：
> 1. 统一"缺字段"策略（建议统一为**抛错 + 明确指出缺哪个字段**），并在文档里写明。
> 2. Word 扫描改为**与 docxtemplater 一致的口径**，或扫描时直接调用 docxtemplater 的 parser 预览，消除"预览/执行不一致"。
> 3. PPT 在 UI 上明确标注"备注页不支持填充"；跨段落占位符给出检测与提示。
> 4. Excel 填充扩展到数字/公式单元格。

## 二、中优先级：能力子集与参数写死（影响"用得上但用不爽"）

### 2.1 图片模块：能用，但每一步都差一点

| 功能 | 关键缺陷 | 证据 |
|---|---|---|
| 批量压缩 | **只有"最长边"一个尺寸参数**，无按宽/高、无目标体积、无百分比 | `ImageView.vue:497` |
| 批量压缩 | **输出不支持 BMP/GIF/AVIF**，但输入过滤器声明支持 gif/bmp | 输入 `:13` vs 输出 `:47` |
| 水印 | **角度写死 -30°**，颜色写死黑色，只能平铺/居中，无九宫格定位 | `:107`、`:111`、`:115-121` |
| 长图拼接 | **不排序，纯按选择顺序**，无法拖拽重排、无法按文件名排序 | `:563`、`:568` |
| 长图拼接 | **无 canvas 高度上限保护**，50 张 1080p 拼图静默失败（空白图） | `:261` |
| 长图拼接 | 质量写死 0.92 | `:281` |
| 证件照 | **强制拉伸变形**（UI 自认），无等比裁剪、无人脸居中 | `:438`、`:667` |
| 证件照 | 相纸只 3 种，质量写死 0.95 | `:381-385`、`:449` |
| 全部图片 tab | **无任何处理前预览** | 全文无 preview canvas |
| 全部图片 tab | **EXIF Orientation 丢失**（竖拍照片显示躺倒）+ 输出抹掉全部 EXIF | `:85-92` |

**最刺痛的两个点**：
- **长图拼接不排序**——用户选 30 张聊天截图，系统对话框顺序即最终顺序，且无法调整。这是最反直觉的设计。
- **长图拼接无尺寸保护**——超限后**静默产出空白图**，用户以为成功了。

> **修复建议（性价比排序）**：
> 1. 拼接增加"按文件名排序"按钮 + 拖拽重排列表 + **canvas 高度上限检测（超限明确报错或分段输出）**。
> 2. 证件照改为**等比 cover 裁剪**（而非拉伸），加简单裁剪框。
> 3. 批量压缩增加"目标体积"和"按百分比缩放"两种常用模式。
> 4. 水印角度/颜色/九宫格定位改为可调。
> 5. 加"处理前预览第一张"能力。

### 2.2 小工具：11 个 tab，每个都"只差一口气"

| 工具 | 缺陷 | 证据 |
|---|---|---|
| 二维码生成 | **宽度写死 260、margin 写死 2、纠错级别未传、无颜色/Logo** | `ToolsView.vue:162` |
| 二维码生成 | 无结构化内容向导（WiFi/vCard/名片等） | 全文 |
| 批量二维码 | 数据源**只认 xlsx/json，不认 csv**（CSV 是批量最常见源） | `:234` |
| 名单加拼音 | **输出只保留"姓名,拼音"两列，丢掉原表其它所有列** | `:424` |
| 名单加拼音 | 输出去向写死，字段名写死，**多音字（单/仇/解）无修正入口** | `:435` |
| UUID | **本轮生成数量写死 5 个**，无输入框，无 v7/格式选项 | `:120` |
| 二维码识别 | **只读第一张图**，不支持批量；**识别失败提示"先裁剪"却没有裁剪入口** | `:340`、`:370` |
| 文件哈希 | 一次只算一种算法，**无"与预期值比对"**（收文件核对哈希是高频需求） | `:606-633` |
| 时间戳 | 16/19 位微秒纳秒会**被当毫秒错算**，无时区、无批量 | `:104` |
| 文本对比 | 无并排视图、无忽略大小写/空白、无导出 diff | `:452` |
| JSON | 无 key 排序、无 JSONPath、无 YAML/XML 互转 | `:513-536` |
| 编解码 | 只有 Base64/URL，无 Hex、无 GBK 文本转码、无 JWT 解码 | `:47` |

**最刺痛的两个点**：
- **名单加拼音丢掉原表所有其它列**——一个"给名单加一列"的工具，本应保留原表全部列并追加一列，这里等于只导出两列，**数据丢失且用户可能直接拿去用**。这是正确性问题，应提到高优先级。
- **二维码识别失败提示"先裁剪"但没有裁剪入口**——把用户导向一个工具里做不到的操作。

### 2.3 压缩/解压：功能太窄

- **打包只能"整个文件夹"**（`zipService.ts:27` 入参只有 `dir`），**不能挑选若干文件**打包——要打包 3 个文件？得先建个文件夹。
- **压缩级别写死 DEFLATE**（`:42`），无"仅存储 / 最高压缩"档位。
- **无打包前文件清单预览**（盲打包）、**无解压前内容预览**。
- **加密 zip 解压报"文件可能损坏"**（`:58`）——实际是加密包不支持，错误信息误导用户。
- **不支持 7z / rar / tar / gz**。
- **整文件读入内存**（`:37`、`:80`），打包数 GB 会爆内存，无大小警告。

---

### 2.4 Excel 工具：多 sheet 静默丢数据

- `splitByRows` / `splitByColumn` / `desensitize` 都只取 `worksheets[0]`（`excelToolsService.ts:166,188,365`）。
- **合并后产生多 sheet 的文件，再用"按行拆分"会静默丢弃其它 sheet**——数据丢了，没有任何提示。
- 脱敏规则固定（`*`、固定保留位数），无正则规则、无自定义脱敏字符（`:348-357`）。
- **仅支持 .xlsx，不支持 .xls**（页面已明示，但无自动转换入口）。

## 三、低优先级：交互与一致性（打磨项）

### 3.1 进度回调"接了线但没通电"

- `officeToPdf` 有 `onProgress` 钩子（`officeToPdfService.ts:125`），**但 `ConvertView.vue:36` 调用时根本没传**。用户看不到"第 3/10 个文件"。

### 3.2 命名策略三处不一致

- 图片批量：`原名 + 新扩展名`（`ImageView.vue:168`）
- 图片拼接/证件照：`exportFilename + 时间戳`（`:287`）
- 小工具：写死 `qrcode_${Date.now()}.png`（`ToolsView.vue:177`）、`名单_带拼音.csv`（`:435`）
- 同名冲突处理行为不统一，有的加 `(1)(2)`，有的可能覆盖。

### 3.3 完成行为不一致

- 比对模式完成后**自动打开结果文件**（`MatchView.vue:129`），匹配填充模式**不自动打开**（`:257-279`）。同一个页面的两个 tab，行为不同。

### 3.4 其他散点

- 二维码批量命名模板支持 `{列名}`，但**空内容行静默跳过，提示仍是"已生成 N 个"，不告知"跳过 X 个"**（`ToolsView.vue:285`）。
- 文件名模式里未匹配的字段静默替换为空串（`namePattern.ts:45`），写 `通知书_{错字段}` 会得到 `通知书_.docx` 而**无警告**。
- 拖入展开用**字符串排序**（`expandService.ts:59`），`img10` 会排在 `img2` 前面（非自然序）。
- `ImageEditor` 导出 JPG 时**静默把透明背景填成白色**（`ImageEditor.vue:947-949`），不告知"JPG 不支持透明"。
- `ImageEditor` 的"扩展画布"与"仅导出选区"同时勾选时，**扩展画布优先**（`:940,955`），但 UI 是两个独立复选框，不提示互斥关系。

## 四、横向共性问题（一句话总结每条）

1. **只读第一个工作表**：`fileUtils.ts:71`、`excelToolsService.ts:166/188/365`、`excelMatchService.ts:23`——全项目普遍，无 sheet 选择器。
2. **数据源不支持 CSV**：批量二维码 `ToolsView.vue:234`、加拼音 `:808`、模板填充 `fileUtils.ts:64-65`。
3. **参数写死清单**：二维码 260/400、margin 2、拼接质量 0.92、证件照 0.95、UUID 5 个、水印角度 -30°、spacing +60。
4. **无预览无确认**：图片全模块、zip 打包、转换、填充、匹配均直接落盘。
5. **失败静默或提示无出路**：批量失败无重试、二维码空行不计数、识别失败指错方向、zip 加密包误报损坏。
6. **同项目内策略不一致**：表头行（合并支持 vs 匹配硬编码）、键归一化（合并归一 vs 匹配不归一）、缺字段（三端不同）、命名（三种）。

## 五、建议的整改优先级

### P0（正确性 / 可信度，必须修）
1. **匹配/比对键归一化统一**（大小写 + 全半角 + 空白），并给 `compareTables` 补重复键警告。
2. **比对/匹配支持 `headerRow` 与工作表选择**，与合并对齐。
3. **名单加拼音保留原表全部列**（当前丢数据）。
4. **环境探测与转换页联动**（未检测到直接禁用并提示）。
5. **长图拼接加 canvas 尺寸上限保护**（当前静默产出空白图）。

### P1（能力补齐，显著提升可用性）
6. 模板填充三端"缺字段/占位符"策略统一 + 预览与执行口径一致。
7. 匹配/比对/Excel 工具补工作表选择器。
8. 图片：拼接排序与拖拽重排、证件照等比裁剪、压缩目标体积模式、水印可调。
9. 小工具：UUID 数量、二维码参数、哈希比对、提取支持 PDF。
10. zip：支持挑选文件打包、压缩级别、加密包正确报错、打包前清单预览。

### P2（打磨，一致性）
11. 命名/冲突策略统一；进度回调接线；完成行为统一；自然序排序；透明通道提示。
